# One number, end to end

This page follows a single number, **MRR on 2026-06-30: $214,743 from 683 active subscriptions**, from the
simulated source system to the dashboard. Every step links to the file that does the work. It is the short way
to read this repo; the [main README](README.md) has the rest.

All data is synthetic, made by [saas-world-sim](https://github.com/sky-five/saas-world-sim) at a pinned tag.
2026-06-30 is the fixed snapshot the metric contract is checked on, so these figures do not move with the
calendar. To get the same warehouse:

```bash
python scripts/run_all.py --fresh --as-of 2026-06-30   # simulate -> load -> dbt build -> dashboard tables
```

```
saas-world-sim ──dlt──> raw_app_db ──dbt──> fct_mrr_daily ──MetricFlow──> metric `mrr` ──> reporting ──> Evidence page
   (source)            (1. load)        (2. model, 3. tests)         (4. semantic layer)              (5. dashboard)
```

## 1. Load: source system to raw tables

- [`pipelines/engine.py`](pipelines/engine.py) is the one place the simulator is imported. It returns the app
  database as it stood at the end of the as-of date.
- [`pipelines/sources.py`](pipelines/sources.py) defines one dlt source per system. Each table loads
  incrementally on its `updated_at` cursor and is merged on its primary key, so a reload never duplicates rows.
- [`pipelines/run.py`](pipelines/run.py) loads them into DuckDB (or Snowflake).

On 2026-06-30, `raw_app_db.subscriptions` has 1,248 rows: 683 active with $214,743 of `mrr_usd`, 565 canceled
with none. `raw_app_db.subscription_changes` has 2,789 rows, one per plan change.

## 2. Model: raw tables to an MRR mart

The mart is not built from the current subscription table but from the change log, so MRR can be read for any
past day.

| Step | File | What it does |
|---|---|---|
| staging | [`stg_app_db__subscription_changes`](dbt/models/staging/app_db/stg_app_db__subscription_changes.sql) | renames and types the change log (generated by [`staging_codegen/`](staging_codegen/)) |
| intermediate | [`int_mrr_movements`](dbt/models/intermediate/int_mrr_movements.sql) | each change that moved MRR, as a delta labelled new, expansion, contraction, churn or reactivation |
| mart | [`fct_mrr_movements`](dbt/models/marts/finance/fct_mrr_movements.sql) | the same rows with money as decimals and an enforced contract |
| mart | [`fct_mrr_daily`](dbt/models/marts/finance/fct_mrr_daily.sql) | every day's movements, then a running total: company MRR on every day |

`fct_mrr_daily` for 2026-06-30 reads $214,743, the same as the raw subscriptions.

## 3. Tests: what stops a wrong number

| Check | Where | Fails when |
|---|---|---|
| dbt unit tests `mrr_movements_types`, `mrr_movements_month_boundary` | [`_finance_models.yml`](dbt/models/marts/finance/_finance_models.yml) | a change is labelled with the wrong movement type, or lands in the wrong month |
| dbt singular test | [`assert_mrr_daily_ties_to_accounts.sql`](dbt/tests/assert_mrr_daily_ties_to_accounts.sql) | the last day's MRR differs from the sum of every account's current MRR by more than a cent |
| dbt singular test | [`assert_invoices_match_mrr_log.sql`](dbt/tests/assert_invoices_match_mrr_log.sql) | an invoice disagrees with the MRR log at the time it was issued |
| pytest | [`tests/test_engine_pin.py`](tests/test_engine_pin.py) | the source rows or the $214,743 total move under the pinned simulator |
| metric glossary | [`metric_glossary/`](metric_glossary/) | a governed metric disagrees with an independent SQL check, month by month |
| metric contract | [`metric_contract/contract.json`](metric_contract/contract.json) | a pull request changes a metric's value on this snapshot without bumping its version |

CI ([`ci.yml`](.github/workflows/ci.yml)) runs all of these; the contract job builds the 2026-06-30 warehouse.

## 4. Semantic layer: one definition of MRR

- [`_semantic_models.yml`](dbt/models/semantic/_semantic_models.yml) declares the measure `mrr_level` on
  `fct_mrr_daily`: a sum over accounts, but the last day of a period, never a sum over days.
- [`_metrics.yml`](dbt/models/semantic/_metrics.yml) turns it into the metric `mrr`, version 1.
- [`semantic/__init__.py`](semantic/__init__.py) queries it through MetricFlow. For June 2026 it returns
  $214,743 and 683 paying accounts.

The dashboard and the [AI analyst](analyst/) both ask MetricFlow, so they cannot disagree on what MRR means.

## 5. Dashboard: semantic layer to the page

- [`scripts/export_reporting.py`](scripts/export_reporting.py) writes the `reporting` tables from MetricFlow
  queries: `kpi_monthly` (June 2026: $214,743) and `kpi_weekly`.
- [`reports/pages/index.md`](reports/pages/index.md) is the Evidence page: the MRR tile reads `kpi_weekly`,
  the month-end MRR vs target chart reads `kpi_monthly`.
- [`nightly.yml`](.github/workflows/nightly.yml) loads one more simulated day every night, rebuilds, and
  publishes to GitHub Pages: **https://sky-five.github.io/ridgeline-analytics/**. The live page shows a later
  date than this walkthrough, so its MRR is higher.

## Checked

[`tests/test_walkthrough.py`](tests/test_walkthrough.py) keeps this page true: every link points to a file that
exists, and the figures quoted here match the simulator and the metric contract. On a warehouse built as of
2026-06-30 it also checks the raw table, `fct_mrr_daily`, the MetricFlow metric and `reporting.kpi_monthly`
all give $214,743 and 683.
